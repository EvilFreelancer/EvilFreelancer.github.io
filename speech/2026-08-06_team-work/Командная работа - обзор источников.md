## 0. Затравка — пост и проект coddy-agent

### Пост evilfreelancer/1734 — согласование Cursor и Claude Code
🔗 https://t.me/evilfreelancer/1734

- **Тип:** заметка из практики (канал автора курса).
- **Суть:** когда в одном проекте работают несколько агентов, у каждого своя папка правил — Cursor берёт `.cursor/rules/*.mdc`, Claude Code `.claude/rules/*.md`. Структура похожа, формат чуть разный, друг о друге они не знают. Решение: держать оба набора в репо, писать правило один раз и синхронизировать вторую папку, оба коммитить.
- **Что взяли:** это **затравка всей лекции** и ядро сегмента 6 (общий контракт команды). Отсюда же ведут ссылки на файлы coddy ниже.

### coddy-agent — `AGENTS.md`
🔗 https://github.com/coddy-project/coddy-agent/blob/main/AGENTS.md

- **Тип:** корневой контракт проекта для агентов.
- **Суть:** проект на четырёх слоях (точка входа CLI → ядро оркестрации `internal/agent` (ReAct) + `internal/session` → внешние каналы HTTP/UI/Telegram/память/планировщик). Принципы: сборка по тегам (только нужные модули), **документация как контракт** (DESIGN.md, OpenAPI, правила в `.cursor/rules/*.mdc`), **тесты перед кодом** (TDD красный→зелёный). Маршрут разработчика: прочитать правила → тесты → реализация → обновить доки → полная регрессия.
- **Что взяли:** живой кейс (сегмент 10) и подтверждение связки «правила + спека + TDD» как контракта команды (сегменты 6–7).

### coddy-agent — `DESIGN.md`
🔗 https://github.com/coddy-project/coddy-agent/blob/main/DESIGN.md

- **Тип:** визуальный контракт встроенного веб-интерфейса (SPA).
- **Суть:** дизайн-токены, границы компонентов и паттерны взаимодействия до того, как код попадёт в прод. Важное для лекции: **мультисессионный стриминг** — SPA ведёт несколько параллельных `POST /v1/responses` по разным сессиям, теневые транскрипты в памяти, чтобы потоки не смешивались; маршрутизация по `#/s/<sessionId>` и заголовку `X-Coddy-Session-ID`.
- **Что взяли:** доказательство модели B «один общий агент» с изолированными мультисессиями (сегменты 8 и 10).

### coddy-agent — `.cursor/rules/workflow.mdc`
🔗 https://github.com/coddy-project/coddy-agent/blob/main/.cursor/rules/workflow.mdc

- **Тип:** правило-воркфлоу для агента.
- **Суть:** BDD/TDD-процесс. Фича: красный (падающий тест) → зелёный (минимум кода) → `make test` → обновить OpenAPI/доки если затронут HTTP → `make lint`. Багфикс: регресс-тест → починка → тесты и линтер. Финальный чек-лист обязательно включает **проброс правил `.cursor/rules/` → `.claude/rules/`**.
- **Что взяли:** конкретный процесс приёмки для сегмента 7 и шаг Rules Sync для сегмента 6.

## 1. Паттерны многоагентности

### Anthropic — «How we built our multi-agent research system»
🔗 https://www.anthropic.com/engineering/multi-agent-research-system

- **Тип:** инженерный разбор от Anthropic.
- **Суть:** архитектура **оркестратор-воркер**. Ведущий агент планирует и запускает 3–5 субагентов параллельно, у каждого свой контекст, чёткая цель, формат и границы; о других субагентах он не знает. В конце ведущий сводит результат. Многоагентная связка обогнала одиночного Opus 4 на **90,2%**. Цена: агент ≈ ×4 токенов к чату, многоагентность ≈ ×15. Не подходит для задач с общим контекстом и кучей зависимостей (а это большинство кодинга). Правило масштабирования усилия: простой запрос — 1 агент, сравнение — 2–4, большое исследование — 10+.
- **Что взяли:** сегменты 3, 4, 5 целиком (изоляция, оркестратор-воркер, когда многоагентность вредит и сколько это стоит).

### Addy Osmani — «The Code Agent Orchestra»
🔗 https://addyosmani.com/blog/code-agent-orchestra/

- **Тип:** обзорная статья про то, что делает многоагентный кодинг рабочим.
- **Суть:** паттерны — субагенты (родитель ведёт граф зависимостей), команды агентов (общий список задач, передача сообщений между напарниками, блокировка файлов), иерархия (оркестратор → фиче-лиды → специалисты). Роль человека: план/спека, одобрение плана, верификация, интеграция. Принципы: специализация > универсал, 3–5 агентов оптимум, сильная спека — рычаг, **не делегируй суждение**, проверка обязательна. AGENTS.md как накопитель общих знаний.
- **Что взяли:** сегменты 4 (паттерны) и 9 (роль человека-тимлида).

## 2. Изоляция и параллельность (git worktrees)

🔗 https://www.augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution
🔗 https://medium.com/google-cloud/run-multiple-coding-agents-safely-with-git-worktrees-c2d237dbd6b2
🔗 https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents

- **Тип:** практические гайды.
- **Суть:** git worktree даёт каждому агенту свою рабочую папку при общем репо — полная изоляция файлов, никаких конфликтов в реальном времени, мерджишь сам и в нужном порядке. Команды гоняют 4–5 агентов разом; для масштаба нужны оркестраторы (Conductor, Vibe Kanban, Claude Squad, Cursor Background Agents и др.). Подводный камень: worktree не делят node_modules/venv — зависимости ставить заново.
- **Что взяли:** сегмент 3 (изоляция работы), демо `git worktree add`.

## 3. Спека и правила как контракт

### GitHub Spec Kit — spec-driven development
🔗 https://github.com/github/spec-kit
🔗 https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/

- **Тип:** open-source тулкит + анонс.
- **Суть:** спека в центре разработки с агентом. Шаги `specify` (что строим) → `plan` (как, архитектура) → `tasks` (разбивка с маркерами `[P]` для параллельных, порядок зависимостей, точные пути файлов, чекпойнты). Markdown-файлы — источник истины. Поддержка 29 интеграций (Claude Code, Cursor, Copilot, Gemini CLI, Codex и др.) — одна спека на любого агента. Контекст-файл по умолчанию `AGENTS.md`.
- **Что взяли:** сегмент 6 (спека как общий контракт для разных агентов).

### Cursor Rules / Claude Code memory — доки
🔗 https://cursor.com/ru/docs/rules · 🔗 https://code.claude.com/docs/en/memory

- **Тип:** официальные доки (источник истины по форматам).
- **Суть:** где и в каком формате живут правила у каждого агента — ровно те папки, которые синхронизируем (`.cursor/rules/*.mdc` и `.claude/rules/*.md`).
- **Что взяли:** сегмент 6, точные пути и форматы. Связь с курсом: модуль 5 (Rules).

## 4. Приёмка: BDD/TDD с агентами

🔗 https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/tdd-with-claude.md
🔗 https://www.nathanfox.net/p/taming-genai-agents-like-claude-code
🔗 https://alexop.dev/posts/custom-tdd-workflow-claude-code-vue/

- **Тип:** гайды и разборы по TDD с агентом.
- **Суть:** проси агента писать тесты первыми и явно говори, что это TDD (иначе агент норовит реализовать сразу и подсунуть заглушки). Цикл красный→зелёный→рефактор даёт агенту чёткую проверяемую цель. Хук PostToolUse автоматически гоняет линтер/тесты после каждой правки. Skill, который заставляет дисциплину red-green-refactor через субагентов, чтобы реализация не «протекала» в тесты внутри одного контекста.
- **Что взяли:** сегмент 7 (тесты как общая граница «готово», хук на тесты/линтер). Связь с курсом: модуль 11 (BDD), модуль 7.2 (Hooks).

## 5. Узкое место — ревью, а не генерация

🔗 https://arxiv.org/abs/2602.19441 — «When AI Teammates Meet Code Review»
🔗 https://blog.cloudflare.com/ai-code-review/ — оркестрация ревью на масштабе

- **Тип:** научная статья + инженерный блог.
- **Суть:** агенты сабмитят PR быстрее, чем команда успевает ревьюить — растёт дисбаланс между скоростью генерации и ёмкостью ревью. «Verification is the bottleneck, not generation». Роль человека смещается в оркестрацию: цели, доступы, ревью результата. Автоматический AI-ревью разгружает очередь (десятки тысяч прогонов, медиана ревью — минуты).
- **Что взяли:** сегмент 2 (узкое место — проверка и сведение) и сегмент 9 (человек-тимлид).
